# 新项目实施路线

日期：2026-10-04｜性质：实施交接说明，不新增正式需求或改变已有技术选型。

## 输入与优先顺序

用户最新决定 → 需求分析 1.1 → 已选技术 1.0 → 当前设计规格 → 可运行原型样本。需求二次检验和测试设计用于核对，而不是替代业务需求。发现冲突时记录涉及编号和具体行为，修订权威文档后再推进受影响部分。

先完整阅读 documents 中五类文档，特别是每条需求属性的 V1/V2/V3 与验证方法。正式需求共101条，其中 V1 90条；后续云同步和扩展不混入首版完成标准。不要把“个人工具”解释为可删除首版 P1。

## 实施顺序与退出条件

| 阶段 | 实施内容 | 进入下一阶段前的证据 |
| --- | --- | --- |
| 0 新工作区与依赖基线 | 核对已有文件，确定新应用根目录；检查 Flutter/Dart 稳定版本与四端构建条件；按选型文档固定依赖 | 不覆盖现有工作；记录 SDK/依赖锁定、原生工具条件和未具备环境。软件安装另按许可处理 |
| 1 领域与本地持久化 | 稳定资产/版本/账号/目标/任务身份，Drift 模型，文件区与操作日志，安全存储边界 | 导入/保存提交与中断恢复契约、故障不破坏已有数据；真正永久副本独立于来源授权 |
| 2 本地图库闭环 | 导入、识别去重、部分成功、整理检索、回收、缺失文件、依赖保护、诊断 | 需求规定的保留/搜索/删除行为有单元和文件系统验证 |
| 3 处理与输出 | 压缩/裁剪/拼接、参数校验、来源与顺序、临时结果、永久保存、导出 | 真实像素、方向、透明/动画/格式能力验证；清理不触及永久图片与活跃依赖 |
| 4 图床与可靠队列 | 两个 ProviderAdapter、多账号、目标快照、持久任务、重试/取消/中断恢复、链接表示 | 每版本×目标结果一致；待确认不盲目重试；离线/授权等待、部分失败与事件乱序有证据 |
| 5 恢复与跨端系统能力 | 设置、缓存保护、完整/元数据备份、暂存恢复、系统照片/文件/分享、权限和后台限制 | 校验失败不覆盖有效数据；四端权限与系统入口分别验证 |
| 6 产品 UI 与首版验收 | 桌面 A、共同业务状态、手机已选候选、窄屏/长名/焦点/读屏，逐条需求覆盖 | 90条 V1 各有对应验证，正式用例与设备证据齐全，文档跟随实现状态 |

阶段之间可按模块交叉实现，但数据保护先于真实文件写入和外部上传。先构建可重复的替身和夹具，再对必须真实验证的依赖进行联调。不要先做一套漂亮的假数据界面，再把持久化、恢复和身份一致性作为后补功能。

## 手机决定未完成时

M1 是推荐候选，M2 仍保留。可完成领域、服务、持久化、桌面 UI 和手机共用展示组件；导航、返回历史和批次入口保持候选隔离。需要最终手机导航定稿时再由用户选定，不能同时拼接两套结构或沿用被否定的旧手机四项底栏。

## 测试与状态报告

documents/unit-test-design.md 提供112个单元场景（V1 102、V2 10）和39个其他验证方案，当前都未执行。按选型转换成实际 Flutter/Dart 测试与系统验证，每个用例保留需求映射。编解码、权限、后台、存储原子性、图床响应和四端设备不是纯单元测试可替代的范围。

每轮报告实际变更、已执行检查和剩余限制。需要安装工具、签名证书、设备、真实图床账号或外部服务时，具体说明缺少什么；不把环境不足改成首版单端范围，也不伪造通过结果。

## 本包无需依赖的内容

旧源码及旧数据库格式、旧项目架构/开发日志、历史界面方案、Figma 生成脚本和额度恢复均不是新应用实施前置条件。可编辑 Figma 的完善仍是设计交付未完成项；直接按当前规格与浏览器样本实施新应用不需要等待其 MCP 服务恢复。
