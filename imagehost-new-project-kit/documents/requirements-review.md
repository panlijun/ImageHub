### 2.2 质量检查原则

组织方向参考 [ISO/IEC/IEEE 29148](https://www.iso.org/standard/72089.html)，条款质量参考 [NASA 系统工程手册附录](https://www.nasa.gov/reference/system-engineering-handbook-appendix/)。重点检查必要性、清晰性、完整性、一致性、唯一性、可验证性、追踪性及技术中立性。不复制付费标准正文，不声称逐条完成正式符合性评估。

| 检查项 | 判定依据 | 结果 |
|---|---|---|
| 必要性 | 能关联到用户边界、现有业务意图或明确的风险完善 | 正式条款均有来源；SRC-O 明示为新版补充 |
| 清晰性 | 参与对象、输入、成功证据及异常动作明确 | 补清重试、超时、回收到期、冲突有效值 |
| 完整性 | 覆盖本地闭环、四端、外部图床及数据保护 | 原项目主要能力都有新版映射 |
| 一致性 | 删除、任务、备份、清理、同步的规则互相兼容 | 关键矛盾已修订，见第 3 章 |
| 唯一性 | 正式编号唯一，任务/尝试/结果身份分离 | 101 个正式编号无重复 |
| 可验证性 | 可从条款得到明确预期，不仅使用“可靠”“快速” | 正式条款均有验收及验证类型 |
| 可追踪性 | 来源—需求—验证方案可以查到双方 | 来源附录与逐需求测试矩阵相互关联 |
| 技术中立性 | 不限制新界面、框架、语言、数据库或 SDK | 旧技术仅在来源审计路径出现 |
| 外部准确性 | 约束有官方来源与核查日期，不放大承诺 | 官方资料以 2026-10-03 核查记录为准，实施前重新核查 |

## 6 最终文档核验与验收界限

Markdown 是统一内容源。最终核验检查正式需求编号及属性、来源引用、测试编号、逐需求覆盖、未来分期、Word 段落/表格顺序、正文、超链接、标题层级和表格结构。对任务、去重、恢复、删除及同步用例，主线程反查预期与需求一致性。

| 验收项 | 合格条件 |
|---|---|
| 交付数量 | 三个主题各有 .md 与 .docx，共六个文件 |
| 需求完整性 | 101 条唯一需求均有来源、优先级、阶段、行为及验收 |
| 首版验证映射 | 90 条 V1 均映射到业务单元测试或明确的其他验证方案；不适合 UT 说明原因 |
| 后续隔离 | 8 条 SYN 与 3 条 EXT 单列，不充当首版已通过证据 |
| 双向追踪 | 用例引用真实需求，矩阵引用真实验证方案，无悬空编号 |
| 格式一致 | 三份 Word 的正文、表格、编号及来源超链接对应同名 Markdown |
| 保护旧文件 | 仅增加独立文档包，原有来源文件保持不变 |
| 诚实说明 | 无测试执行结果、标准认证或未完成视觉验证的夸大声明 |

按用户已选验收方式，Word 完成内容与结构核验，**未进行逐页视觉验收**。最终呈现的分页、跨页表格及特定 Word 软件字体替换未作实机视觉确认。此限制不影响 Markdown 内容源的业务基线，但不能据此宣称打印版逐页排版已验收。
